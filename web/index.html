A cache from scratch — hit, miss, TTL

A cache is a fast key→value store in front of a slow source. A hit is served from cache; a miss falls through to the (slow) database and populates the cache for next time. Read the same keys and watch the hit rate — and DB load — improve.

The proof: the first read of a key misses and pays the DB (≈150ms); every repeat is a hit (≈1ms) and skips the DB. Locality (a few keys get most traffic) is why a small cache lifts the hit rate fast. TTL is your staleness safety net — expire, and those keys miss once more.

LRU eviction — the O(1) recency trick

A cache can't grow forever, so at capacity it must evict. LRU drops the least-recently-used key — betting "recently used → used again soon". Access a key and it jumps to the most-recently-used end; the front of the line is always the next victim.

Access keys and watch the least-recently-used one get evicted.

The proof: the Map remembers insertion order; on access we delete-and-reinsert so the key moves to the MRU end, and the first entry is always the LRU victim — all O(1). LRU's weakness (next panel): a one-pass scan of cold keys evicts your whole hot set.

FIFO · LRU · LFU · W-TinyLFU

LRU bets on recency, LFU on frequency, W-TinyLFU admits by frequency (a scan's one-hit keys never displace the hot set). Run a skewed workload, then a scan, and compare hit rates.

Run a workload to compare the four policies.

The proof: on a skew, frequency-aware policies win. On a scan, LRU and FIFO collapse — each burst of cold keys flushes the hot set — while LFU and W-TinyLFU reject the one-hit-wonders and protect it. W-TinyLFU is best-or-tied on both workloads (its small recency window keeps LRU's edge on skew), which is why Caffeine ships it.

Cache-aside — the dominant read pattern

The cache sits to the side of the DB; the app coordinates. Read: try cache → on miss, query DB and populate. Write: update the DB and invalidate the key so the next read repopulates.

Read once (miss), again (hits), then write and read again.
0DB queries
—last read

The proof: the first read misses (150ms DB); repeats are ~1ms hits. A write invalidates the key, so the next read misses once more and repopulates. Simple and resilient — if the cache is down you just always miss (degraded, not broken). The subtle stale-read race is panel 6.

Write-aside · write-through · write-back

Reads are easy; writes hold the trade-offs. Write-through keeps the cache warm but pays DB latency every write; write-back is fastest but if the cache dies before the flush, those writes are gone.

The proof: write-through updates both synchronously (consistent, but you pay ~100ms DB latency and cache things that may never be read). Write-back returns instantly and coalesces repeats, but a crash before flush loses the dirty set — great for counters/metrics, never for money.

Cache stampede (thundering herd)

A hot key expires and, in the same instant, every in-flight request misses and hammers the DB to recompute the same value. Three fixes: single-flight (one recomputes, the rest share), jittered TTL, and stale-while-revalidate (serve stale, refresh in the background).

Run it with no fix, then single-flight, then SWR.
—DB calls
—requests served

The proof: naive → 50 DB calls (the herd), the cache aimed a firehose at the DB. Single-flight coalesces to 1. SWR serves the stale value to all 50 instantly and does 0 blocking calls (one background refresh). Pick by shape: one hot key → single-flight; many keys expiring together → jitter; staleness OK → SWR.

Probabilistic early expiration (XFetch)

The lock-free stampede fix: on each read of a near-expiry key, flip a weighted coin to refresh early. One lucky request recomputes just ahead of the TTL, so the herd never synchronizes — no lock, no coordination. Rule: refresh if now − Δ·β·ln(rand) ≥ expiry.

β (eagerness)1.0
Run hard-TTL, then XFetch, and compare the recompute spikes.
recomputes per tick ·

The proof: hard TTL fires the whole herd at each expiry (a spike of ~10). XFetch spreads recomputes to at most ~1 per tick — one request refreshes ahead of the cliff, everyone else keeps hitting the fresh value. Higher β refreshes earlier/more often. It composes with jitter and single-flight.

The read-repair race — stale forever

"Write DB, delete cache key" sounds safe, but a slow reader can interleave and leave the cache holding a stale value until TTL. Step the race, then turn on versioned/CAS writes to reject the stale write.

cachek = (empty)

The proof: the delete "happened" — but before the slow reader wrote back the v1 it read earlier, so the cache serves v1 forever while the DB says v2. Fixes: a TTL backstop (bounds the damage), delayed double-delete, versioned/CAS (reject a write whose version is stale), or CDC-driven eviction decoupled from request timing.

Cache penetration — a bloom filter guard

A cache only accelerates keys that exist. A flood of requests for nonexistent keys misses the cache every time and hammers the DB. A bloom filter rejects "definitely absent" keys in O(1) (with a small false-positive rate); short-TTL negative caching handles the rest.

Run it with the bloom off, then on.
—DB queries
—bloom false-positive rate

The proof: without a guard, 500 bogus keys → 500 DB queries (the cache protected nothing). A bloom preloaded with the real keys short-circuits ~98% as "definitely absent" — DB queries drop to the residual false-positive fraction. Pair it with short-TTL negative caching, minding the read-after-create gotcha.

Hot keys — the celebrity problem

One key (a celebrity, a flash sale) takes a huge share of traffic and hotspots a single shard. Hot reads want a near-cache or key replication; hot writes want a sharded counter — different directions, different tools.

Send the burst with no mitigation, then near-cache, then replicate.

The proof: unmitigated, one shard eats all 10,000 reads. A near-cache (L1 on each app server) drops the shared L2 to ~one warm-up per server; replicating the value across N keys spreads it ~N×. Neither helps hot writes — that needs a sharded counter (write a random shard, sum on read).

Cache-down resilience — survive a cold cache

When the cache goes cold (flush, restart, node loss) all traffic hits the DB at once. A concurrency limiter caps in-flight DB queries and a circuit breaker sheds the rest fast — so the DB serves what it can and recovers, instead of collapsing.

Run it with the protection off, then on.
success rate per round · DB capacity is the dashed line

The proof: naive → the DB is drowned every round (in-flight ≫ capacity), goodput stays ~0% and the cache can't even refill — metastable. The limiter holds in-flight ≤ capacity and the breaker fails fast, so a bounded fraction is served, the DB stays healthy, and as the cache warms the success rate recovers to 100%.

Consistent hashing — add a node without a miss storm

node = hash(key) % N remaps almost every key when N changes — a cache-wide miss storm. A hash ring with virtual nodes moves only ~1/N of keys when you add or remove one.

Add a node under each scheme and compare how many keys remap.
—of 10,000 keys remapped on the last change

The proof: naive modulo remaps ~80–100% of keys on a single add — every one becomes a miss that stampedes the DB. On the ring only the keys in one arc move (~1/N), and virtual nodes keep the arcs even so no node is overloaded. This is why every real distributed cache uses it.

Sizing — the back-of-envelope math

Sizing is a formula, not a guess: DB load = QPS × (1 − hit) (nonlinear — the last few percent shed the most), memory = working-set × overhead × replicas × headroom, and average latency = hit × cache + miss × DB. Drag the knobs.
